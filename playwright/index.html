En detalle

Las cuatro decisiones que separan una suite de Playwright que el equipo mantiene solo de una que acaba desactivada en el pipeline. No son decisiones de herramienta: son decisiones de arquitectura, y casi todas se toman en la primera semana.

1. Una estructura de proyecto que aguanta mil tests

El error más caro de los primeros días es espejar la estructura del código de la aplicación. Los tests no siguen al código: siguen al negocio. Si tu producto se reorganiza en microservicios, la suite no debería enterarse.

La estructura que uso separa por qué se prueba, no por dónde vive el código que lo implementa:

tests/
  e2e/          checkout.spec.ts, alta-usuario.spec.ts…
  api/          contratos y llamadas directas, sin navegador
fixtures/
  auth.ts       sesiones ya autenticadas
  datos.ts      alta y limpieza de datos por test
pages/          localizadores y acciones. Cero asserts
playwright.config.ts

La regla que mantiene esto ordenado es sencilla: un spec es un flujo de negocio que alguien puede nombrar en una reunión. «Checkout con tarjeta rechazada» es un spec. «Validaciones del componente Input» no lo es — eso es un test unitario que está en el sitio equivocado y que vas a pagar en minutos de CI todos los días.

Los projects no son sólo para navegadores

La mayoría de equipos usa projects únicamente para lanzar la suite en Chromium, Firefox y WebKit. Su uso más rentable es otro: un proyecto de setup que se autentica una vez y guarda el estado, del que dependen los demás. Se acaban los logins repetidos en cada test, que suelen ser el primer tercio del tiempo total de ejecución.

// playwright.config.ts
export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: '.auth/user.json' },
      dependencies: ['setup'],
    },
  ],
});

El entorno se resuelve con variables (process.env.BASE_URL), no con un archivo de configuración por entorno. Un solo playwright.config.ts, siempre.

2. Fixtures frente a page objects: no compiten

Es la discusión más repetida y casi siempre está mal planteada, porque las dos piezas resuelven problemas distintos:

  • Un fixture es ciclo de vida. Monta algo antes del test, lo desmonta después y lo inyecta. Usuario autenticado, pedido de prueba, feature flag activo.
  • Un page object es vocabulario. Cómo se llaman las cosas de una pantalla y qué se puede hacer en ella.

La mezcla que duele es un page object que guarda estado entre tests o que hace expect por dentro. Cuando eso falla, el mensaje de error habla de un selector, no de lo que esperaba el negocio, y depurarlo cuesta el triple. Los asserts van en el spec, siempre.

Lo natural es que el fixture entregue el page object ya en su sitio:

export const test = base.extend<{ checkout: CheckoutPage }>({
  checkout: async ({ page }, use) => {
    const checkout = new CheckoutPage(page);
    await checkout.irAlCarritoConUnArticulo();
    await use(checkout);
    await checkout.limpiarCarrito();
  },
});

Criterio para decidir en dos segundos: si hay que crearlo y destruirlo, es un fixture; si es «cómo se llama este botón», es un page object.

Localizadores: getByRole antes que CSS

Un test que se rompe porque alguien renombró una clase de CSS no estaba probando negocio, estaba probando marcado. Los localizadores por rol accesible (getByRole('button', { name: 'Pagar' })) sobreviven a los rediseños y, de paso, fallan cuando la accesibilidad se rompe. Es la única forma de cobertura de accesibilidad que sale gratis.

3. Playwright en CI sin tests inestables

Dos conceptos que se confunden constantemente: los workers son paralelismo dentro de una máquina; los shards reparten la suite entre varias máquinas. Se combinan, y es lo que convierte cuarenta minutos en ocho.

strategy:
  matrix:
    shard: [1/4, 2/4, 3/4, 4/4]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }} --reporter=blob
  # y un job final que une los informes:
  - run: npx playwright merge-reports --reporter=html ./all-blob-reports

Sin merge-reports acabas con cuatro informes parciales que nadie abre. Con él, un único HTML donde el fallo se ve en dos clics.

Reintentos: útiles, y peligrosos

retries: process.env.CI ? 2 : 0 es la configuración razonable. Pero conviene tener clara la trampa: un test que sólo pasa al segundo intento no es un test verde, es un fallo pendiente. Los reintentos compran tiempo para investigar, no sustituyen la investigación. Si el porcentaje de tests inestables no se mide y no tiene dueño, la suite se degrada sola en unos meses y el equipo aprende a ignorar el rojo — que es el final de toda inversión en automatización.

Para que investigar sea barato:

  • trace: 'on-first-retry' — traza completa sólo cuando algo falla. Cuesta cero en las ejecuciones buenas.
  • video: 'retain-on-failure' — el vídeo se descarta si el test pasa.
  • El informe HTML publicado como artefacto del pipeline, enlazado desde el propio pull request.

Y un objetivo de tiempo que conviene defender: si la suite crítica no cabe en diez minutos, el equipo dejará de esperarla y empezará a mergear sin mirar. A partir de ahí, el problema ya no es técnico.

4. Migrar desde Selenium, Cypress o Protractor

La migración que casi siempre fracasa es la traducción literal, test por test. Un port 1:1 arrastra al framework nuevo todos los defectos del viejo: las esperas artificiales, los selectores frágiles, los tests que prueban cuatro cosas a la vez. Terminas con la misma suite ingobernable, sólo que en TypeScript.

Lo que funciona es convivencia con fecha de caducidad:

  1. Las dos suites corren en el mismo pipeline. La antigua sigue siendo la red de seguridad y nadie toca el delivery.
  2. La suite nueva crece por criticidad de negocio: primero los flujos que bloquean facturación, después los que más incidencias generan en producción, y el resto al final o nunca.
  3. Se fija un criterio de apagado explícito y por escrito — por ejemplo, veinte ejecuciones consecutivas estables cubriendo los flujos críticos.
  4. Cumplido el criterio, la suite antigua se borra. Dos suites conviviendo para siempre es el peor de los dos mundos: doble mantenimiento y ninguna en la que confiar del todo.

Hay dos cosas que no se traducen, se eliminan. Los Thread.sleep y los waits explícitos de Selenium desaparecen: Playwright espera solo antes de cada acción, y mantener esperas manuales encima de eso sólo suma tiempo y ruido. Y los cy.wait('@alias') de Cypress se sustituyen por esperar el efecto visible en la interfaz, que es lo que de verdad le importa al usuario.

Dudas frecuentes

Preguntas que me hacen antes de empezar

¿Playwright o Cypress?

Para proyectos nuevos, Playwright: multi-navegador real, paralelismo nativo sin coste de licencia y ejecución de API y UI en la misma suite. Si ya tienes una suite de Cypress sana y el equipo la mantiene sin dolor, migrar por migrar no renta. La pregunta correcta no es cuál es mejor, sino qué te está costando hoy la que tienes.

¿Cuánto se tarda en montar un framework desde cero?

La arquitectura base con fixtures, autenticación, datos aislados y ejecución en CI son días, no meses. Lo que lleva tiempo es la cobertura, y esa crece flujo a flujo con el equipo, no de golpe.

¿Sirve Playwright para pruebas de API?

Sí, y es una de sus mejores bazas: request permite preparar datos por API y validar el resultado en la interfaz dentro del mismo test. Para pruebas de contrato entre servicios sigo prefiriendo Karate DSL, que está diseñado para eso.

¿En qué lenguaje conviene escribirlo?

TypeScript salvo motivo de peso. Es donde Playwright tiene la API más completa y la comunidad más grande. Si tu equipo de desarrollo es Java o Python, a veces compensa alinearse con ellos para que mantengan la suite: que el equipo pueda leerla importa más que el lenguaje.

¿Hay que cambiar de sistema de CI?

No. Playwright corre igual en GitHub Actions, Azure DevOps, GitLab CI o Jenkins. Trabajo sobre el pipeline que ya tienes.

¿Podremos mantenerlo sin ti?

Ese es el objetivo declarado del encargo. Pair-programming sobre el código real, documentación en el propio repositorio y rotación del rol de responsable de la suite desde el primer mes. Si al terminar dependes de mí, el trabajo ha salido mal.
